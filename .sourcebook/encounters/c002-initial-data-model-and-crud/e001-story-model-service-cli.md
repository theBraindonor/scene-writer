# E001 — Story Model, Service, and CLI

## Requirements
- Add `SQLAlchemy` and `typer` as runtime dependencies of the project (`[project.dependencies]`), not dev-only tooling.
- Add a SQLAlchemy ORM `Story` model to `scene.data`, matching the `story` table defined in `docs/data-model.md` (`id`, `title`, `style_guidance`, `scenario`, `is_archived`), including its non-null/non-empty and archived-flag constraints.
- Add SQLAlchemy engine/session infrastructure to `scene.data` that defaults to a SQLite file under a top-level `data/` folder, while allowing the database URL to be overridden (so tests do not read or write the real project database).
- Add `data/*.db*` (and related SQLite sidecar files) to `.gitignore`; keep the `data/` folder itself present in git (e.g. via a placeholder file) even though its database contents are ignored.
- Add a `scene.core` service module wrapping story CRUD operations (create, get, list, update, archive/unarchive) against the `scene.data` `Story` model, giving both the CLI and future LLM agents one shared interface.
- Add a single Typer-based CLI program, `scene-data`, registered as a project console script, with a `story` sub-command group (`scene-data story ...`) exposing story CRUD through `scene.core`.
- Cover the new `scene.data` model, `scene.core` service functions, and `scene.cli` story commands with unit tests, mirroring `src/` under `test/` per the `unit-testing` lore, using an isolated (non-production) database for every test.

## Rationale
This is the first encounter of `c002-initial-data-model-and-crud`. It establishes the full vertical slice — ORM model, service layer, and CLI — for a single entity (`story`), the root object in `docs/data-model.md`'s proposed schema, before the campaign extends the pattern to scenes, characters, locations, and renderings. It also introduces concrete tooling choices not yet reflected in project lore: SQLAlchemy for the ORM and Typer for the CLI.

## Plan
1. Add `sqlalchemy` and `typer` to `[project] dependencies` in `pyproject.toml` (as runtime dependencies, distinct from the `dev` group), and update `pdm.lock`.
2. In `scene.data`, add a declarative `Base` model class, an engine/session-factory helper that resolves a default SQLite URL under `data/` (e.g. `data/scene.db`) but accepts an override URL, and a `Story` model matching `docs/data-model.md`'s `story` table and constraints.
3. Add `data/*.db*` to `.gitignore`, and add a placeholder (e.g. `data/.gitkeep`) so the `data/` folder itself stays tracked in git.
4. In `scene.core`, add a `story` service module with functions to create, get, list, update, and archive/unarchive a story, operating through `scene.data`'s session/engine helpers.
5. In `scene.cli`, add a `scene-data` Typer application with a `story` sub-command group calling into `scene.core.story`, and register `scene-data` as a `[project.scripts]` console entry point.
6. Add unit tests under `test/scene/data`, `test/scene/core`, and `test/scene/cli` covering the new `Story` model (including its constraints), the `scene.core.story` service functions, and the `scene-data story` CLI commands (via Typer's test runner), all running against an isolated test database rather than the real `data/` file.
